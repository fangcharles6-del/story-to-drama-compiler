# SDC-ADR-043: Generated Reference Candidate Provenance and Qualification Boundary

- Status: Accepted
- Date: 2026-08-29
- Depends on: SDC-ADR-039 / Deterministic Visual Prompt Profiles
- Projection dependency: SDC-ADR-040 / Visual Prompt Profiles Phase 1 Projection Manifest
- Compiler-boundary dependency: SDC-ADR-041 / Visual Prompt Profiles Compiler Integration
- Reference-Prompt dependency: SDC-ADR-042 / Character and Scene Reference Prompt Compiler Input
  Boundary
- Baseline: `c1ad6ed62b138403050bfe4304d8e5a7e9eca526`
- Authority: `HUMAN_GATE / NOT_AUTHORIZED`
- Candidate-capture data boundary: one exact ADR-042 reference Prompt Artifact, one caller-supplied
  immutable Provider Attempt Outcome document containing unauthenticated origin claims and at most
  one exact locally supplied PNG output
- Qualification data boundary: one exact Candidate closure, the exact locally supplied PNG bytes,
  the exact ten bounded retained evidence documents and privacy-minimized preparer/qualifier
  identity records reviewed by a human qualifier; integrity closure does not authenticate an
  external Provider, prove rights or authorize use
- Network/spend boundary: zero network calls, zero credential reads, zero Provider requests, zero
  authorized Attempts and zero authorized cost

## Context

SDC-ADR-039 and SDC-ADR-040 establish an offline first-party Profile Catalog, deterministic Prompt
rendering and zero-authority Receipts. SDC-ADR-041 preserves the released Compiler identity through
an opt-in narrative Prompt sidecar. SDC-ADR-042 then adds an independent character-or-scene
reference Prompt Compiler boundary whose Artifact binds one supplied Bible, one active imported
primary asset, one exact five-value Profile selection, one Snapshot, one render input, exact Prompt
bytes and one process Receipt.

The accepted ADR-042 BUILD is present at the baseline above. The Schema Registry contains exactly
72 models: the pre-ADR-041 68 models, the two ADR-041 models and the two ADR-042 models. Existing v1,
Creative Sample v2, narrative sidecar and reference Prompt Artifact identities and committed Schema
bytes are released compatibility boundaries.

No released formal contract represents generated reference media as a Candidate. Several existing
names are superficially similar but do not close this gap:

- `CharacterAssetVersion` and `SceneAssetVersion` hard-code
  `provenance=IMPORTED_APPROVED_MEDIA`, including in their ID projections;
- Runtime events named `candidate.generated` are operational strings, not immutable media Candidate
  contracts;
- `AttemptRecord` and `ArtifactRecord` are mutable persistence rows and may hide earlier Attempts or
  non-current outputs;
- `ProviderRequest`, `ProviderTaskSnapshot` and `DownloadedArtifact` do not bind the ADR-042 Profile,
  Snapshot, render input, Prompt Receipt, rights, privacy, retention or Qualification closure;
- the existing real-asset Qualification and Rights Manifest chain is fixed to the imported 14-member
  pack and `ASSET_INTAKE_ONLY`; and
- Profile recipe roles describe intended reference-sheet semantics. They are not generated media
  slots, Candidate identities, role assignments or Provider input materials.

ADR-039 through ADR-042 permanently prohibit relabeling generated bytes as
`IMPORTED_APPROVED_MEDIA`, even after download, human review or re-import. They require a separate
provenance and Qualification decision before any generated-reference promotion path can be
considered.

This ADR proposes that missing boundary. It is an architecture decision only. While it remains
Proposed it reserves no digest domain, approves no implementation, creates no Candidate, performs
no Qualification and authorizes no Provider or Runtime activity.

## Decision summary

If Accepted, the first generated-reference Candidate slice will:

- remain an isolated offline evidence-admission and verification boundary;
- accept one exact revalidated ADR-042 Artifact without changing or recompiling it;
- accept one immutable caller-supplied Provider Attempt Outcome evidence packet;
- support Attempt 1 only and exactly one expected, reported and byte-verified PNG output for a
  successful V1 Outcome;
- create one immutable `CAPTURED_UNQUALIFIED` Candidate for that one verified output only;
- represent Provider origin as an explicit assertion backed by bound evidence, not as authenticated
  external truth;
- bind the full Profile/Artifact/Prompt/Receipt closure, Attempt evidence and exact output bytes into
  a new domain-separated Candidate identity;
- keep Candidate capture separate from human Qualification, Rights Manifest review, current-status
  assessment and promotion;
- define a separate finite human Qualification Request and Decision whose positive outcome means
  only `PASS_FOR_SEPARATE_GENERATED_RIGHTS_MANIFEST_REVIEW`; and
- only after a separate BUILD is approved, append exactly four top-level formal contracts and four
  committed Schema files.

The first slice will not:

- submit, inspect, download, cancel or retry a Provider task;
- accept multiple outputs or infer first/latest/best output selection;
- create role-specific images from the three-character-role or four-scene-role Profile tuples;
- modify a Candidate after Qualification or rights review;
- create a Rights Manifest, current-status record, promoted AssetVersion or Bible binding;
- connect any new value to `GenerationJob`, `JobGraph`, `ProviderRequest`, `InputMaterial`, Runtime,
  Temporal, PostgreSQL, QC automation or publication; or
- grant remote-processing, retention, training, commercial-use, promotion or execution authority.

## Proposed acceptance record and implementation gate

Acceptance of this ADR would explicitly confirm these four trade-offs:

1. immutable caller-asserted evidence capture rather than Provider authentication or Runtime
   integration: the first BUILD may validate internal closure but may not produce evidence through a
   Provider call;
2. Attempt 1 and exactly one verified PNG output rather than premature Retry or multi-output policy;
3. a scoped Qualification result that only enables separate generated-rights-manifest review rather
   than rights or promotion; and
4. a separate future promotion/current-status boundary before any multiple-role Provider-input
   design or executable route.

Acceptance would also freeze exactly four future top-level contracts and their append order. It
would not approve that BUILD. A later BUILD must start from a newly verified authoritative `main`,
remain isolated, use only first-party synthetic known answers and pass every gate below before its
Draft PR can be approved.

## Terminology and lifecycle

The following states are distinct:

1. **Reference Prompt Artifact**: the ADR-042 offline Compiler result. It contains no generated
   media and authorizes no Attempt.
2. **Provider Attempt Outcome**: immutable supplied evidence about one historical or synthetic
   Attempt. It is not an instruction to perform an Attempt.
3. **Generated Reference Candidate**: one exact generated output occurrence, bound to one exact
   successful Attempt Outcome and exact media bytes. It starts and remains
   `CAPTURED_UNQUALIFIED` in its own immutable document.
4. **Qualification Request**: a finite, expiring request for an independent human decision over one
   exact Candidate and exact retained evidence.
5. **Qualification Decision**: an immutable scoped historical decision. A positive decision makes
   only the exact Candidate eligible for separate generated Rights Manifest review.
6. **Generated Rights Manifest**: a future generated-specific rights closure. This ADR defines its
   required inputs but creates no such contract.
7. **Current-status evidence**: future append-only expiry, hold and revocation evidence, including a
   `SUPERSEDED` revocation reason. It never rewrites the Candidate or Qualification Decision.
8. **Promotion**: a future atomic decision that may create an append-only generated eligible-asset
   or versioned binding. No promotion output exists in this ADR.

Candidate capture is not Qualification. Qualification is not Rights Manifest closure. Rights
Manifest closure is not current-status proof. None of those states is Provider-input, execution,
publication, retention or training authority.

## Offline evidence-admission boundary

A conforming future V1 Candidate-capture operation will receive only:

- one exact `CreativeSampleReferenceVisualPromptArtifactV1` value;
- one exact future `CreativeSampleGeneratedReferenceProviderAttemptOutcomeV1` value;
- for a verified-success Outcome only, one caller-designated local PNG path whose expected raw
  digest and size are already present in the Outcome; and
- no Catalog lookup, Provider client, environment configuration, credential, clock, randomness,
  filesystem discovery or mutable global selection policy.

The operation must revalidate the Artifact under its released exact type and recompute every
existing Artifact, Profile, render-input, raw Prompt and Prompt Receipt digest using the original
accepted domains. It must not issue a replacement Snapshot digest: ADR-042 has no independent
Snapshot hash, and the Snapshot is already closed through the Profile and Artifact projections.

The operation validates the internal consistency of caller assertions. It does not receive the
retained authorization, submitted-request, Provider-task, terms or terminal-observation source
records and therefore cannot authenticate those historical claims. It must state that limitation in
its result. Presence of their claimed digests is required structurally; semantic review of the exact
retained bytes occurs only at Qualification.

The local output path is transport-only input. The verifier must resolve one explicitly named path,
reject directories, symlinks and ReparsePoints, hold one open handle while inspecting, reject
path/file-identity or size drift, read the file under a fixed bound, validate the frozen PNG technical
record and compare exact bytes with the Outcome. No path enters a portable identity or persistent
formal document.

A separate future Qualification-request operation receives the exact Artifact, Outcome, Candidate,
the exact locally supplied PNG bytes, exactly ten caller-supplied retained canonical JSON evidence
documents and two privacy-minimized preparer identity records. It repeats the safe local-file
admission procedure, recomputes the raw PNG and technical-record digests, recomputes every retained
JSON document SHA-256 and size, closes them against the Candidate and evidence-reference tuple and
prepares a finite human review request. Decision creation additionally receives the same exact PNG
bytes, the same ten evidence documents and the two exact privacy-minimized qualifier identity
records; it repeats every byte/digest check before accepting the human result. The human qualifier
must review a rendering decoded from those exact admitted PNG bytes, not a thumbnail, URL or
unbound copy. The local path is transport-only and never enters a projection. The human qualifier,
not the Candidate-capture code, assesses external meaning and sufficiency.

Failure returns no Candidate, writes no file and performs no external action.

## Attempt and terminal-state rules

All V1 Outcomes describe caller-asserted Attempt 1 only. Exact submission and terminal-observation
timestamps are required and `submitted_at <= terminal_observed_at`. One claimed Provider request is
always recorded. A pre-POST local failure is not a Provider Attempt Outcome and cannot be represented
by this contract.

The claimed Provider terms must satisfy `provider_terms_observed_at <= submitted_at` and
`provider_terms_valid_from <= submitted_at < provider_terms_valid_until` when the latter is finite.
This is temporal consistency of the caller assertion, not authentication of the terms record.

The remaining terminal fields obey this exact matrix:

| Disposition | Provider task reference | Reported count | Overflow | Verified count | Descriptors | Reason code |
| --- | --- | ---: | --- | ---: | ---: | --- |
| `VERIFIED_SUCCESS` | present | 1 | false | 1 | one ordinal-0 descriptor | null |
| `SUBMISSION_REJECTED` | absent | 0 | false | 0 | empty | required |
| `PROVIDER_TASK_FAILED` | present | 0 | false | 0 | empty | required |
| `CANCELLED` | present | 0 | false | 0 | empty | required |
| `EXPIRED` | present | 0 | false | 0 | empty | required |
| `SUBMISSION_UNKNOWN` | present or absent | 0 | false | 0 | empty | required |
| `PARTIAL_OUTPUT` | present | 0..1 | false | 0 | empty | required |
| `OUTPUT_INTEGRITY_FAILURE` | present | 1 | false | 0 | empty | required |
| `UNSUPPORTED_OUTPUT_CARDINALITY` | present | 2..64, or 64 | false, or true | 0 | empty | required |

The non-null reason literal is uniquely derived from the disposition:

```text
SUBMISSION_REJECTED_BY_PROVIDER
PROVIDER_TASK_REPORTED_FAILURE
PROVIDER_TASK_CANCELLED
PROVIDER_TASK_EXPIRED_OR_TIMED_OUT
SUBMISSION_RESULT_UNKNOWN
EXPECTED_OUTPUT_NOT_FULLY_AVAILABLE
OUTPUT_BYTES_OR_TECHNICAL_RECORD_MISMATCH
PROVIDER_REPORTED_UNSUPPORTED_OUTPUT_COUNT
```

The order above matches the eight non-success dispositions. Provider error codes and messages remain
only in the retained terminal-observation record and never enter this field.

For `UNSUPPORTED_OUTPUT_CARDINALITY`, `overflow=false` means the bounded count is exact in `2..64`.
`overflow=true` requires the bounded value 64 and means `AT_LEAST_65`; the retained terminal
observation records the overflow without selecting or describing any output. For every disposition,
`verified_output_count == len(output_descriptors)`. No non-success Outcome may contain a descriptor.

`PARTIAL_OUTPUT` with reported count zero represents a Provider task that reached a terminal
success/completion shape but reported none of the one expected output. Reported count one represents
one expected output occurrence that was reported but was not fully available for exact-byte
verification; bytes that are available but fail raw or technical integrity instead use
`OUTPUT_INTEGRITY_FAILURE`. Neither form may be misreported as `PROVIDER_TASK_FAILED`, which requires
the Provider task itself to report failure.

`SUBMISSION_UNKNOWN` permits either Provider-task-reference status because uncertainty can arise
before an accepted task reference is retained or after one has been retained. A present reference
remains only an opaque fact inside the retained terminal-observation/provenance records; no raw task
ID enters the portable Outcome. Presence does not authorize inspection, cancellation, download,
re-POST or Retry and does not make the submission known.

`VERIFIED_SUCCESS` additionally requires the submitted Prompt raw digest and size to equal the
ADR-042 Artifact, all duplicated Artifact/Profile/Receipt fields to agree and the one local PNG to
match the exact descriptor and technical record. Candidate capture checks these internal claims. It
does not authenticate the retained attempt, authorization or terms records; that is a Qualification
gate.

Qualification assesses whether authorization and terms were effective at `submitted_at`. Their
later expiry does not erase the historical Outcome or Candidate. It may prevent a new Qualification
Request, expire a Decision or produce a non-current future rights/status assessment.

Every other disposition is ineligible for Candidate capture. `SUBMISSION_UNKNOWN` always stops at
`HUMAN_GATE`, never authorizes re-POST and cannot be used as the predecessor of a V1 Retry because V1
does not represent Attempt 2 at all. If later evidence resolves an unknown submission, a future
append-only Outcome-resolution or V2 contract must link to the original Outcome; the original is
never overwritten.

Inspection or download transport retries for the same Provider task remain observations inside one
Attempt. They are not a new Creative Attempt. Any future Attempt 2 requires a separate ADR/version,
an explicit retry authorization and a new provenance chain. Qualification failure never creates
Retry authority.

## Output descriptor and output-set identity

The inline V1 output descriptor contains exactly:

```text
ordinal=0
media_type=image/png
content_sha256: raw LowerSha256
size_bytes: exact integer in 1..67108864
technical_record: exact inline PNG technical-record value below
technical_record_sha256: LowerSha256
regular_file_verified=true
symlink_absent=true
reparse_point_absent=true
admission_transform_performed=false
```

The raw `content_sha256` is SHA-256 over the exact PNG bytes and has no domain.
`admission_transform_performed=false` states only that the local admission verifier did not change
the bytes; it does not prove that the Provider-to-local transport performed no transformation.

The exact PNG technical-record projection is:

```text
media_type=image/png
width: exact integer in 512..4096
height: exact integer in 512..4096
bit_depth=8
color_space: RGB | RGBA
alpha_status: ABSENT | OPAQUE | NON_OPAQUE
interlaced=false
animation_frame_count=1
metadata_status: ABSENT | PRESENT
metadata_chunk_types: ordered unique tuple of 0..32 PNG ancillary chunk type strings
png_signature_valid=true
ihdr_count=1
idat_present=true
iend_count=1
chunk_crc_valid=true
unknown_critical_chunk_absent=true
apng_chunks_absent=true
trailing_bytes_count=0
decompressed_pixel_bytes: exact integer in 786432..67108864
```

Its digest is:

```text
sha256(
  b"sdc:generated-reference-png-technical-record:v1\0"
  || canonical_compact_json(the exact PNG technical-record projection)
).hexdigest()
```

The parser must validate the PNG signature, bounded chunk lengths, CRC for every chunk, legal chunk
order, exactly one IHDR and IEND, at least one IDAT, no bytes after IEND, color type 2 or 6 only,
8-bit non-interlaced pixels, exactly one frame, no `acTL`/`fcTL`/`fdAT` chunks, no `tRNS` chunk,
bounded decompression and exact decoded pixel-byte count. Unknown critical chunks fail. The parser
also enforces at most 1,024 total chunks, at most 512 IDAT chunks, at most 64 ancillary chunks and at
most 1,048,576 cumulative ancillary payload bytes, rejecting a limit crossing before further
allocation or decompression. Ancillary chunk contents are not copied into the document; only their
unique chunk types in first-occurrence file order are recorded.
`decompressed_pixel_bytes` must equal `width * height * 3` for RGB or
`width * height * 4` for RGBA. RGB requires `alpha_status=ABSENT`; prohibiting `tRNS` ensures this
does not conceal palette-style transparency. RGBA requires `OPAQUE` only when every decoded alpha
sample is 255 and otherwise requires `NON_OPAQUE`. `metadata_status=ABSENT` if
and only if `metadata_chunk_types` is empty. Metadata presence and non-opaque alpha are captured
truthfully rather than silently repaired. Human Qualification decides whether they are acceptable.

The V1 Output Set projection contains `expected_output_count`,
`reported_output_count_bounded`, `reported_output_count_overflow`, `verified_output_count` and the
ordered descriptor tuple. Its digest is:

```text
sha256(
  b"sdc:generated-reference-provider-output-set:v1\0"
  || canonical_compact_json(the exact Output Set projection)
).hexdigest()
```

V1 accepts one output only. If a Provider reports more than one output, the Outcome records the
bounded exact count or explicit `AT_LEAST_65` overflow state under
`UNSUPPORTED_OUTPUT_CARDINALITY`; it records no descriptor, selects no output and creates no
Candidate. A future version may admit a bounded ordered Output Set, but it must still create one
distinct Candidate per output occurrence. It must not deduplicate equal bytes across Attempts or
interpret an output ordinal as a Profile recipe role.

## Candidate identity

The Candidate semantic digest is:

```text
sha256(
  b"sdc:generated-reference-candidate:v1\0"
  || canonical_compact_json(the exact Candidate projection)
```

- Profile constraints and QC expectations are contextual evidence only; and
- semantic QC recommendations cannot automatically pass or fail a gate.

retroactively cure an unauthorized submission, retention or training event.
Manifest review at `as_of < decision_at`, `as_of == qualification_valid_until` or later must fail
closed; an expired Decision requires a new Qualification Request and Decision. A manifest completed
while the Decision is valid may later be assessed under its own frozen validity/current-status
rules; consumers must not reinterpret the expired Qualification Decision itself as current evidence.

## Expiry, hold and revocation

Candidate, Attempt Outcome, Qualification Request and Qualification Decision documents are
immutable historical evidence. They are never edited to express current status.

A future generated-reference current-status boundary must use append-only evidence and expose these
closed assessment results:

```text
CURRENT
EXPIRED
HELD
REVOKED
INDETERMINATE
```

Required semantics are:

- `as_of` is an explicit UTC-second input;
- `as_of == valid_until` is expired;
- hold, revocation, privacy complaint, Provider terms change and a revocation whose reason is
  `SUPERSEDED` are new evidence, not Candidate mutations;
- confirmed prohibited training use or a confirmed retention/deletion violation is revocation
  evidence; newly discovered but unresolved training use, or a passed deletion deadline without
  exact deletion proof, produces `HELD` or `INDETERMINATE` under the future frozen policy and can
  never remain `CURRENT` merely because no earlier revocation record existed;
- absence of a revocation record is not proof of `CURRENT`;
- missing, stale, forked or incomplete observation chains produce `INDETERMINATE`;
- `REVOKED` and `HELD` dominate positive historical Qualification; and
- consumers must bind the exact status evidence and assessment receipt used at their explicit
  `as_of`.

This ADR does not add a status Schema. A separate status/rights BUILD or ADR must freeze observation
chain identity, freshness windows, privacy-minimized evidence and record-as-of assessment before
promotion can be designed. Existing real-asset fresh-status contracts cannot be reinterpreted
because their subject closure is the imported pack and use-plan chain.

## Promotion interface and permanent V1 prohibition

Current `CharacterAssetVersion` and `SceneAssetVersion` remain permanently unavailable as promotion
targets for generated bytes. Their IDs bind the literal `IMPORTED_APPROVED_MEDIA`; human review,
copying, downloading or re-importing cannot change origin.

A future promotion decision must atomically consume and revalidate:

- the exact Candidate and raw media bytes;
- the exact successful Attempt Outcome and ADR-042 Artifact;
- a positive, unexpired generated Candidate Qualification Decision;
- a generated-specific Rights Manifest;
- a complete generated-reference current-status assessment equal to `CURRENT` at an explicit
  `as_of`; and
- exact subject, asset-purpose and any separately reviewed role-assignment evidence.

The future output must be append-only: either a generated-media AssetVersion/Bible V2 family or the
typed eligible-asset sidecar direction selected by ADR-039. It must not mutate the existing primary
AssetVersion, reinterpret a V1 provenance literal or silently replace a Bible's active binding.

This ADR chooses neither promotion representation and creates no promotion eligibility.
`eligible_for_asset_promotion=false` remains exact in all four proposed contracts.

## Multiple reference-role and Provider-input dependency

One V1 Candidate is one composite reference-sheet PNG. The character Profile's three reference
asset types and the scene Profile's four reference asset types remain authored recipe semantics.
They do not prove that the composite image contains each view, do not split the PNG into media and
do not assign any output to a Provider-input role.

The required dependency order is:

1. this Candidate provenance and Qualification ADR;
2. a generated Rights/current-status and promotion boundary that defines a truthful post-promotion
   eligible asset or sidecar;
3. a separate Multi-Reference Role Binding / Provider Input Material V2 ADR; and
4. a later execution-integration ADR for Runtime, Provider, network, credentials, cost and Retry.

The first Provider-input version must accept only post-Qualification, rights-closed,
current-status-verified and post-promotion values. A pre-promotion Candidate may be cited as evidence
but cannot become executable merely because it exists or has a positive Qualification Decision.

If a later design wishes to submit a qualified-but-unpromoted Candidate, it must first supersede
this ordering through a new explicit ADR, define that state and define its separate remote-processing
authorization. It cannot treat the possibility as an exception inside this decision or add an
implicit union to `InputMaterial` or `ProviderRequest`.

## Zero-authority boundary

Each proposed top-level contract directly carries the complete false/zero authority surface listed
in its projection plus the machine-readable
`authority_scope=THIS_DOCUMENT_GRANTS_NO_PROVIDER_RUNTIME_OR_ASSET_USE_AUTHORITY`. Direct authority is never inherited from an
Artifact, Attempt record, human review, Profile status, Catalog compatibility observation, valid
hash or successful output.

In particular:

- a separately bound historical execution authorization is evidence about the past, not permission
  for another request;
- `attempt_ordinal` and `observed_provider_request_count` are historical evidence, not authorized
  counts;
- `PromptRenderReceipt` remains process evidence and not a Rights Manifest or approval;
- Profile Catalog qualification, rights and compatibility fields remain zero-authority metadata;
- Candidate capture is not Qualification;
- a positive Qualification Decision grants no rights or promotion; and
- no document in this ADR enables publication, retention, training, Provider selection, Retry or
  automated execution.

`authorized_attempts=0`, `provider_requests=0`, `authorized_cost_cny=0` and `posts_allowed=0` remain
exact JSON integers, not booleans or documentation claims. Every direct authority boolean remains an
exact JSON `false`.

## Prompt, QC, Provider and rights isolation

The existing responsibility split remains unchanged:

- positive and negative Profile constraints are deterministic Prompt text;
- `qc_expectations` are contextual expectations that do not enter Prompt bytes and do not become
  image facts;
- semantic QC remains advisory and cannot issue a Qualification Decision;
- Provider compatibility observations cannot choose a Provider or model;
- the Artifact and Receipt prove only deterministic local process integrity;
- Attempt Outcome and Candidate documents bind supplied evidence without authenticating the
  Provider independently; and
- human Qualification and Rights Manifest review remain separate scoped decisions.

No Prompt constraint becomes a QC, copyright, privacy, likeness, brand or commercial-use fact. No QC
result becomes provenance, rights or promotion authority.

## Runtime and execution isolation

Any future conforming first BUILD must be structurally and operationally inert:

- no Runtime, Provider, client, workflow, worker, persistence or QC module imports the new module;
- no new contract is accepted by `GenerationJob`, `JobGraph`, `ProviderRequest`, `InputMaterial`,
  Canary execution or Temporal workflow input;
- no Provider adapter accepts a Candidate, Qualification value or Artifact through duck typing;
- no network, credential, environment variable, mutable configuration, clock or random value is
  read;
- no Provider task is submitted, inspected, downloaded, cancelled or retried;
- no media is created, copied, transformed, retained, uploaded, published or trained on;
- no PostgreSQL row, Runtime event, Candidate state, AssetVersion or Bible is written; and
- all direct authority and future-action counts remain false/zero.

The future module must not import `sdc.schemas`. Registry wiring is one-way: `sdc.schemas` may import
the four top-level models only after separate BUILD approval.

## Validation operations and honest claim levels

A future verifier may expose separate operations or results equivalent to:

1. **STRUCTURAL_INTEGRITY_VALID**: one document satisfies its exact type and semantic digest.
2. **CLOSURE_VALID_AGAINST_SUPPLIED_EVIDENCE**: exact supplied Artifact, Outcome, Candidate and local
   bytes agree under their released projections.
3. **QUALIFICATION_DECISION_VALID**: one exact Decision closes one exact Request and Candidate under
   the exact policy and validity window against supplied human reference/action records; it is not
   external identity authentication or attestation.
4. **CURRENT_STATUS_UNVERIFIED**: the only honest default until a separate generated current-status
   evidence chain is supplied and assessed.

Integrity-only validation must not be reported as Provider authentication, rights clearance,
current status or promotion eligibility. A missing historical Catalog may make renewed Profile
admission unverifiable even when the embedded Artifact remains internally valid.

## Resource, privacy and retained-evidence boundary

Every new top-level document, retained evidence document and retained human identity/action record
uses the actual ADR-040 persistent canonical-document codec: UTF-8 without BOM, all strings and keys
already NFC, recursive key sorting, two-space indentation, `ensure_ascii=false`, `allow_nan=false`,
LF only and exactly one terminal LF. Arrays preserve their frozen semantic order. Raw document
SHA-256 values are over those exact pretty-printed persistent bytes. This is distinct from the
ADR-040 compact, no-terminal-LF codec used only for semantic digest projections, including the
frozen policy projection. Raw admission rejects
invalid UTF-8, duplicate keys, missing fields, extra fields, explicit null where not admitted,
coercion, subclass values, noncanonical text and scalar-type substitution. Literal and zero-authority
fields are required in persistent documents and are never silently defaulted.

The future first BUILD must impose at least these bounds:

- each new ADR-043 top-level JSON document: `1..262144` bytes before parsing; the supplied ADR-042
  Artifact retains its released `1..524288` boundary;
- nesting depth at most 16 and each generic container at most 64 items;
- Prompt bytes: the existing ADR-042 `1..65536` limit;
- exactly one PNG output: `1..67108864` bytes;
- width and height: `512..4096` each;
- no path, URL, binary media, credential, raw Provider identifier or unbounded response payload in a
  formal document; and
- bounded NFC human text with control-character and bidi-control rejection.

Media admission must reject symlinks, ReparsePoints, non-regular files, size drift and path/content
TOCTOU. The operation reads one explicitly supplied path once into a content-addressed verification
step and never discovers files recursively.

Retained records containing Provider identifiers, reviewer identity, rights documents or sensitive
details remain outside portable contracts. Formal documents bind only privacy-minimized portable
references and exact digests. The contracts do not authorize retaining those records; retention must
already be separately approved.

## Failure behavior

The future boundary fails closed for at least:

- a value that is not one exact revalidated ADR-042 Artifact;
- any Artifact, Profile, Catalog, render-input, Prompt or Receipt digest mismatch;
- any subject, purpose, active AssetVersion or source/Outcome cross-variant mismatch;
- any attempt to label generated output as `IMPORTED_APPROVED_MEDIA`;
- a missing required claim digest during Outcome/Candidate capture, or retained Qualification bytes
  whose digest, size, freshness or submission-time effective scope does not match the Request;
- a raw Provider task ID, URL, path, credential or unbounded error value in a formal document;
- any Attempt ordinal other than one or any predecessor/retry field in V1;
- an attempt to capture a Candidate from a non-success, unknown, partial, extra-output or
  integrity-failure Outcome; the Outcome may remain valid historical evidence under its matrix;
- a missing, non-regular, linked, replaced, oversized, invalid or mismatched PNG;
- any output ordinal other than zero in V1;
- an unknown field, coercible scalar, noncanonical string, unordered tuple or unrecognized enum;
- any semantic digest, full-hash/short-ID or raw-byte digest mismatch;
- an incomplete, stale, aliased or expired Qualification evidence set;
- a Decision outside the Request window or by the same retained identity as the preparer;
- a positive Decision with any non-PASS gate or issue code;
- any non-false/non-zero direct authority value; and
- any attempt to send an Artifact, Outcome, Candidate, Request or Decision into an execution path.

Failure produces no replacement value, performs no fallback or default selection and never chooses
latest evidence, first output, best image, nearest Profile, alternate Provider or Retry.

## Rejected alternatives

This ADR rejects:

- relabeling, importing or promoting generated bytes under `IMPORTED_APPROVED_MEDIA`;
- adding a generated provenance enum member to current AssetVersion contracts;
- treating download, human review or re-import as a provenance transformation;
- treating `candidate.generated`, `DownloadedArtifact`, `ArtifactRecord` or `AttemptRecord` as the
  formal Candidate;
- reusing the imported 14-member pack Qualification or Rights Manifest scope;
- using the current undomained Provider request fingerprint as Candidate identity;
- deriving an identity from incidental Pydantic serialization or a generic `stable_id` helper;
- including local paths, raw Provider IDs, signed URLs, credentials or response bodies in portable
  evidence;
- mutating a Candidate to `QUALIFIED`, `REVOKED` or `PROMOTED`;
- automatically retrying after unknown submission, failure or Qualification rejection;
- selecting first/latest/best from multiple Provider outputs;
- deduplicating equal media bytes across Attempts into one Candidate;
- inferring three or four role-specific media values from one composite reference sheet;
- accepting a Candidate directly as current `InputMaterial` or Provider input;
- treating Profile constraints, QC expectations or Catalog compatibility as output facts;
- automatically creating a Rights Manifest, AssetVersion, Bible binding or publication record; and
- adding Runtime, Provider, network, credential, persistence or paid-service code to the first BUILD.

| Blocking | Caller-supplied Provider evidence is mistaken for external authentication | Keep the Candidate unqualified, state asserted assurance explicitly and require independent human evidence review |

| Blocking | Historical positive review is mistaken for current unrevoked status | Use exclusive validity and require future append-only as-of status evidence; absence means INDETERMINATE |

## Permitted claims and explicit non-proofs

Only after a separately approved conforming implementation may SDC claim that:

- one exact supplied ADR-042 Artifact, one exact supplied Attempt Outcome and one exact verified PNG
  occurrence produced one immutable unqualified Candidate identity;
- the Candidate binds the supplied Profile/Prompt/Receipt, Attempt and output-byte evidence without
  changing existing Compiler outputs;
- one exact finite human Qualification Request produced one exact scoped Decision under the frozen
  policy and validity window; and
- all documents remain offline and grant zero Provider, Runtime, rights, asset-use, publication,
  promotion or execution authority; a positive Decision only routes the exact Candidate to a
  separate generated Rights Manifest review.

Even then, SDC may not claim that:

- a structurally valid supplied Outcome proves that the external Provider actually performed the
  task;
- a structurally valid Qualification Decision externally authenticates the preparer or qualifier;
- the Prompt, source text, input media or output is owned, licensed or commercially usable;
- any real person, likeness, privacy, sensitive-data, brand or protected-content question is cleared
  outside the exact reviewed evidence;
- a positive Qualification Decision is a Rights Manifest or current-status proof;
- absence of revocation evidence means the Candidate is current;
- the Candidate is an approved AssetVersion or role-specific Provider input;
- Profile constraints or QC expectations were achieved in the image;
- a Provider is capable, available, entitled, affordable or authorized;
- Retry, retention, training, publication, promotion or execution is permitted; or
- future equal media bytes inherit this Candidate's Qualification or rights state.

## Consequences

Positive consequences:

- generated reference media gains a truthful identity without corrupting imported AssetVersion
  semantics;
- Prompt, Attempt and media-byte evidence form one explicit deterministic closure;
- mutable Runtime state and immutable portable evidence remain distinct;
- Qualification becomes a finite human decision rather than an inferred effect of generation;
- rights, privacy, retention, training, revocation and promotion remain visible independent gates;
- single-output V1 avoids premature multi-output and role-assignment ambiguity; and
- all released v1, Creative Sample v2, Profile and Prompt Artifact bytes remain compatible.

Costs and limitations:

- the first BUILD cannot itself obtain real Provider evidence or create a usable asset;
- a positive Qualification Decision still requires generated Rights Manifest, current-status and
  promotion work;
- multi-output and role-specific Provider input remain deferred;
- explicit evidence projections and known answers add review overhead; and
- any future field, domain, output-cardinality or promotion change requires a versioned decision and
  renewed compatibility review.
